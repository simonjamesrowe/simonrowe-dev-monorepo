Architecture Kafka Event-Driven

The outbox pattern: reliable events without distributed transactions

SR Simon RoweHead of Engineering, Global
24 Apr 2026 9 min read
cover — 16:7

Almost every event-driven system starts with the same innocent line of code: save a row, then publish a message. It works on your machine. It works in the demo. Then one day the broker is briefly unreachable after the database commit, the message is never sent, and two services quietly disagree about reality.

This is the dual-write problem, and you can't solve it by wrapping a database transaction and a Kafka send in the same try block — they're two separate systems with no shared commit. The fix I reach for every time is the transactional outbox.

The core idea

Instead of writing to the database and the broker, you only ever write to the database. The event is inserted into an outbox table in the same local transaction as your business change. A separate process then reads that table and publishes to Kafka.

One transaction, one source of truth. If the business write commits, the event exists. If it rolls back, so does the event.

What the write looks like

The aggregate and its event are persisted atomically — there is no window where one exists without the other.

@Transactional
public Order place(OrderRequest req) {
  var order = orderRepository.save(Order.from(req));
  outbox.save(new OutboxEvent(
      "order.placed",            // type
      order.id(),                   // aggregate id
      avro.serialize(order)         // schema-registry payload
  ));
  return order;                    // both commit together
}

Getting it onto the topic

A relay moves rows from the outbox to Kafka. You have two good options:

  • Change Data Capture (Debezium tailing the WAL) — lowest latency, no polling, but more infrastructure to run.
  • A polling publisher — a scheduled job that claims unpublished rows, sends them, and marks them done. Boring, debuggable, and good enough for most teams.

Don't forget idempotency

The relay guarantees at-least-once delivery, which means consumers will occasionally see a duplicate. Make the consumer idempotent — key on the event id, dedupe on the read side, and a redelivery becomes a non-event rather than a double order.

When it's worth it

Not every service needs this. If you're emitting fire-and-forget analytics, skip it. But the moment an event drives money, inventory, or another service's state, the outbox is the cheapest insurance you'll ever buy. It's saved me from the 2am "why are these two systems disagreeing" page more times than I can count.

I'll go deeper on the polling-relay implementation — claim batching, backoff, and poison-message handling — in a follow-up. Until then: stop dual-writing.
